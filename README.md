# CGC Core

Cognitive Governance Cycle — Olympus Mont Systems' AI decision-governance engine.

Every AI decision routed through CGC Core is: pre-filtered against agent/RBAC/scope rules, scored by four independent governance modules, evaluated against compliance frameworks, cryptographically sealed with a non-repudiable signature (Proof of Decision), and written to an immutable, hash-chained audit trail. Consumed today by LedgiProof and LedgiProof Tax Pro as a server-to-server governance layer for AI-assisted transaction classification, by ControlMiles for crash monitoring and trip-governance sealing, and by Xolphi (self-signed-up, not a first-party allowlisted app) for runtime error monitoring and launch-readiness tracking — see [`sdk/python/`](sdk/python/) / [`sdk/js/`](sdk/js/) if you're integrating a new one.

## Architecture

```
request → PreFilter → SCM (security gate) → ┬→ PAN (pattern analysis)
                                              ├→ ECM (evaluation/calibration)
                                              ├→ PFM (probability/failure modeling)
                                              ├→ SDA (standards/domain adherence)
                                              ├→ weighted aggregation
                                              ├→ ComplianceEngine (EU AI Act / NIST RMF)
                                              ├→ PoD (cryptographic seal)
                                              ├→ TCO (immutable audit log)
                                              └→ response
```

| Module | Path | Role |
| --- | --- | --- |
| PreFilter | `app/modules/prefilter/` | Agent/RBAC/scope gate, first line of defense |
| SCM | `app/modules/scm/` | Security & Cryptographic Module — signing, encryption, KMS |
| PAN / ECM / PFM / SDA | `app/modules/{pan,ecm,pfm,sda}/` | The four scoring modules aggregated into a decision |
| ComplianceEngine | `app/modules/compliance/` | Evaluates decisions against EU AI Act / NIST RMF criteria |
| PoD | `app/modules/pod/` | Proof of Decision — pre-delivery cryptographic non-repudiation |
| TCO | `app/modules/tco/` | Immutable, hash-chained audit trail |
| LOOP | `app/modules/loop/` | Orchestrates the full cycle above (`cgc_loop.py`) |
| Guard | `app/modules/guard/` | Rate limiting, credential-stuffing/payload detection, internal misuse detection, circuit breaker, tenant action policies, kill switch |
| Flow Scoring | `app/modules/flow_scoring/` | Rolling business-flow health signals per connected app |
| JLA | `app/modules/jla/` | Governance calibration data loader (`cgc_jla.*` schema) |
| Launch Readiness | `api/v1/endpoints/launch_readiness.py` | Play Store/App Store submission-readiness tracking per app_source |

`app/Core/` holds cross-cutting infrastructure: `db/` (Postgres connection pooling + schema provisioning), `auth/` (JWT + session auth), `tenant/` (plan/quota management), `logging/`, `config/`.

## Data & tenant isolation

Postgres (Supabase), schemas `cgc_pod` / `cgc_tco` / `cgc_guard` / `cgc_jla` / `cgc_auth`. Two application-level DB roles:

- **`postgres`** — DDL, boot-time schema provisioning, and every cross-tenant admin read (dashboards, billing). Bypasses RLS by design.
- **`cgc_app`** — real Row-Level-Security-enforced role for tenant-scoped writes/reads (PoD's 3 tables, the 4 tenant-scoped `cgc_guard` tables, and — as of 2026-09-14 — `cgc_tco.audit_trail` reads).

  **`cgc_tco.audit_trail` is now DB-enforced, closed 2026-09-14** (previously app-code-only). The table's `tenant_id` column was already known unreliable — for `app_source='ledgiproof'`, it holds dozens of ad-hoc testing/debug strings (`cgc-concurrency-test-001`, etc.), not a real per-tenant identifier, which is why an earlier `tenant_id`-based RLS policy here had been dropped as actively wrong. That only ruled out `tenant_id`, not RLS itself: `app_source` — the column TCO's own reads have always actually filtered by, indexed, populated on every row — works. `Database.get_scoped_connection()` now accepts an `app_source` parameter (a deliberately separate session variable, `cgc.current_app_source`, from `tenant_id`'s own — reusing it would silently reintroduce the same bad-data problem), and `get_audit_trail_by_app()`/`get_decision_timeseries()` (backing `/governance/reports`, `/governance/timeseries`, `/tenants/my-apps/{app_source}/decisions`) read through it. Verified with two rows sharing an identical (messy) `tenant_id` but different `app_source`, connected AS the RLS-restricted `cgc_app` role (not the bypass-RLS admin role): each scope saw only its own row, an unscoped connection saw zero. Writes still go through the unrestricted admin connection permanently, by design — this table is one global sequential hash chain, and scoping the block-numbering write would corrupt it, not isolate it. See `docs/INTEGRATION_GUIDE.md` §7.2 for what this means for an external integrator.

  **Public-schema PostgREST exposure, two passes, both closed 2026-09-14.** First pass (six tables: `cgc_launch_errors`, `cgc_launch_snapshot`, `cgc_launch_checklist_items`, `cgc_tenant_webhooks`, `cgc_saml_connections`, `cgc_calibration_changelog`) found Supabase's default `anon`/`authenticated` PostgREST grants never revoked — `cgc_saml_connections` and `cgc_tenant_webhooks` being world-writable via the public anon key was the most severe. A second advisor sweep the same day found 16 more tables and 2 `SECURITY DEFINER` views (`v_decision_summary`, `v_forensic_audit`) carrying the identical pattern. Both passes were fixed live in the database, but only the second is codified: `Database._lock_down_public_schema_grants()` (the final step in `scripts/run_schema_migrations.py`) revokes `anon`/`authenticated` on every table found across both passes and adds an explicit `deny_all USING(false)` policy — so a fresh environment bootstrapped from the migration script alone now reproduces the same locked-down state, not just the live database that received the fix by hand. Verified via Supabase's own advisor (`rls_enabled_no_policy`: 22 → 0, `security_definer_view`: 2 → 0) and a disposable Postgres container re-running the full migration idempotently. This app never uses PostgREST (talks to Postgres directly via `psycopg2`), so none of this was ever needed by the app itself — pure exposure closed, not a feature regression.

## Running locally

```
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Without `DATABASE_URL` set, `Database` falls back to local JSON files under `data/` (dev-only — not safe on a read-only filesystem, e.g. Vercel outside `/tmp`).

## API surface

Interactive docs at `/docs` (Swagger) once running. `sdk/python/` and `sdk/js/` (both package `cgc-core-sdk`) wrap the self-service integration surface below for Python and TypeScript/JavaScript callers — see either README for install/usage; no SDK exists yet for any other language. `docs/API_VERSIONING_POLICY.md` documents what changes are breaking vs. non-breaking and the process for introducing a `/v2` if one's ever needed (none has been yet — there is exactly one, unversioned surface today; `root_path="/api/v1"` is cosmetic, OpenAPI doc URLs only).

Key routes: `POST /governance/decision` (the main entry point), `POST /auth/signup` / `signin`, `GET /verify/{decision_id}` (unauthenticated forensic proof lookup, gated by knowing the decision_id + tenant), `GET /dashboard` (operator UI), `GET /health`, `GET`/`PUT /calibration/{module}/{area}` + `GET /calibration/changelog/list` (versioned history of PAN/ECM/PFM/SDA scoring-rule changes — every update is admin-only and always changelogged in the same request, no code path updates calibration silently), `GET /governance/scoring-methodology` (the exact aggregation formula and every area+sensitivity weight, for an auditor who doesn't want to read source), `GET /compliance/glba-safeguards` (FTC Safeguards Rule self-assessment — see Known Gaps below for why GLBA, not HIPAA/FINRA, is the framework that actually applies), `POST /tenants/self-signup` (any authenticated non-admin user can claim a brand-new, not-yet-taken `app_source` and get its API key — reserved first-party names can't be self-claimed, and this can't touch any other tenant's data), `GET /tenants/my-apps` + `POST /tenants/my-apps/{app_source}/keys/regenerate` + `POST .../keys/{key_id}/revoke` + `.../billing/checkout-link` + `.../billing/portal-link` (customer self-service, ownership-checked against `created_by` rather than `require_admin` — the backend for `GET /dashboard/account` below), `GET /dashboard/account` (the one customer-facing settings page — claim an app, see your own keys, regenerate/revoke them, upgrade/manage your own billing; deliberately standalone, not linked from the internal-ops dashboards' topnav), `GET`/`POST`/`DELETE /tenants/my-apps/{app_source}/webhook` (register a URL to receive an HMAC-SHA256-signed POST on every decision for your app_source instead of polling — best-effort delivery, 5s timeout; a failed delivery is now queued and retried on a 5-tier backoff, see `POST /admin/webhooks/process-retries` below), `POST /admin/webhooks/process-retries` (require_admin_or_service, cron-callable — works through `cgc_webhook_retry_queue` on a 5m/15m/1h/4h/24h backoff, 5 attempts max, then gives up permanently; run every 10 minutes by `.github/workflows/webhook_retries.yml`), `GET`/`PUT`/`DELETE /tenants/my-apps/{app_source}/weighting/{area}/{sensitivity_level}` (per-tenant override of the ECM/PFM/PAN/SDA decision-weighting matrix — ownership-checked, weights validated to sum to ~1.0; falls back to the global hardcoded matrix when no override is set), `POST /admin/keys/rotation-check` (require_admin_or_service, cron-callable — Slack-alerts on any active key older than 90 days; never rotates anything itself), `GET /docs/getting-started` (a real, hand-written integration guide with curl examples — signup, self-signup, first decision, webhook signature verification, rate limits — complementing, not duplicating, the auto-generated Swagger at `/docs`), `GET /tenants/my-apps/{app_source}/decisions` (customer-facing decision history — reuses TCO's existing `get_audit_trail_by_app`, capped at the 100 most recent, ownership-checked like the rest of the `/tenants/my-apps/*` family — the backend for `/dashboard/account`'s Decision History tab), `GET /auth/google/status` + `GET /auth/google/login` + `GET /auth/google/callback` ("Continue with Google" — Google OIDC login for `/dashboard/account`, no auth dependency since these are login entry points; see Required environment variables for the 3 vars that turn it on), `GET /auth/saml/lookup` + `GET /auth/saml/{domain}/login` + `POST /auth/saml/{domain}/acs` + `GET /auth/saml/metadata` (enterprise SAML SSO — Okta/Azure AD/OneLogin — one connection per customer email domain, admin-provisioned via `POST`/`GET /admin/saml-connections`, no auth dependency on the login-flow routes since they're entry points; uses `python3-saml` for all cryptographic verification, never hand-rolled), `GET`/`PUT`/`DELETE /tenants/my-apps/{app_source}/action-policies[/{action}]` (self-service, per-action BLOCK/REQUIRE_HUMAN_REVIEW rules, optionally conditioned on area/data domains — see Known Gaps → Already Mitigated below for the full action-governance stack this belongs to), `POST /tenants/my-apps/{app_source}/kill-switch/activate` + `.../deactivate` + `GET .../kill-switch` (self-service emergency stop for your own `app_source`), `GET /guard/activity/circuit-breakers[/reset]` + `GET /guard/activity/kill-switches[/activate|/deactivate]` (operator-only — dashboard visibility and manual override for the circuit breaker and kill switch, including the platform-wide `GLOBAL` scope), `GET`/`POST /tenants/my-apps/{app_source}/agents` + `GET`/`PUT`/`DELETE .../agents/{agent_id}` (self-service agent registry — register a real agent with its own `roles`/`scopes`/`capabilities`, then pass its id as `agent_id` on `POST /governance/decision` to have PreFilter evaluate against it instead of the default synthesized agent; omitting `agent_id` keeps today's behavior unchanged).

## Known gaps

These are the real, currently-unmitigated gaps as of 2026-09-15 — kept accurate deliberately, since this file is the first thing an external auditor or acquirer would check against the actual code:

- **No third-party security audit or penetration test.** Only internal self-testing has been done (SQL injection, auth bypass, rate-limiting, email-vector checks) — no independent firm has verified this.
- **`AWS_KMS_MASTER_KEY_ID` isn't provisioned** — SCM signs locally, not through a FIPS-validated hardware boundary.
- **No ISO/IEC 42001, SOC 2, or other independent certification.** ComplianceEngine evaluates against EU AI Act / NIST RMF / GLBA Safeguards Rule criteria internally, but nothing here is externally certified.
- **No third-party cryptographic audit of PoD/TCO's hash-chain design** — nothing external has verified it's actually tamper-resistant against an insider with direct Postgres access.
- **Several GLBA Safeguards Rule elements are genuinely `MANUAL_REVIEW_REQUIRED`** (Qualified Individual designation, written risk assessment, written security program, service-provider oversight from the covered entity's side) — organizational/personnel facts no code can attest to, honestly reported as such by `GET /compliance/glba-safeguards` rather than assumed. `incident_response` and `periodic_testing` currently report `FAIL` for real (Slack alerting isn't configured everywhere, and no third-party pentest exists — see above).
- **Zero external paying customers.** Every current consumer (LedgiProof, LedgiProof Tax Pro, ControlMiles, Xolphi) is the same operator's own product — no independent market validation yet.
- **SAML self-service domain verification is same-domain-email only** (2026-09-14) — proves the caller holds a mailbox at the domain they're claiming, not that they're actual IT/admin staff there. A stronger check (DNS TXT record) is a real follow-up, not done yet. The operator's admin path (`POST /admin/saml-connections`) still exists unchanged for direct provisioning.
- **No IdP-initiated SSO or JIT role/group provisioning.** SAML login here is SP-initiated only (start at CGC Core, not from a tile inside the customer's Okta dashboard); a new SAML user gets the same default `user` role Google/password signup gets, with no group-to-role mapping.
- **No SDK outside Python and TypeScript/JavaScript** (`sdk/python/`, `sdk/js/`, both 2026-09-14) — every other language integrates by hand.
- **Webhook retries are best-effort, not guaranteed.** The 5-tier backoff (2026-09-14) gives up permanently after 5 attempts with no dead-letter surface beyond a log line — a customer whose endpoint is down for more than ~24h loses that notification for good.
- **A handful of unprefixed `public` tables** (`decisions`, `decisions_2026_04/05/06`, `pod_chain`, `prefilter_results`, `decision_modules`) exist in production but aren't created by any current migration step — found 2026-09-14 while closing the PostgREST exposure gap below (their `anon`/`authenticated` grants were revoked along with everything else), but whether they're genuinely dead legacy schema or still read by something not yet found hasn't been determined.
- **`cgc_guard.app_billing` is also missing from `run_schema_migrations.py`** — found 2026-09-14 testing the SSRF fix in a genuinely fresh environment (self-signup crashed with `UndefinedTable` there); exists in production (created some other way, pre-dating this migration system, like the unprefixed tables above), so no live impact, but a truly fresh bootstrap is still incomplete. Not yet codified.
- **Per-tenant API keys can't manage their own webhook or weighting-override config** — found 2026-09-14 testing the SSRF fix. `AuthSystem.verify_token()` gives a per-tenant API key principal a synthetic email (`apikey@<app_source>`), but `set_my_webhook`/`get_my_webhook`/`delete_my_webhook` and the weighting-override endpoints check ownership via `_owns_app_source(app_source, user["email"])`, which compares against the real `created_by` email and can never match. Only a session JWT (from `/auth/signin`) can currently manage these — `/monitor/*` and `/launch-readiness/*`'s newer `_bound_app_source()`-style checks don't have this problem, and neither does the new agent registry below (its ownership check is the same `_owns_app_source` call, same limitation). Not yet fixed.
- **The agent registry (below) has no capability/scope-granting UI or workflow yet** — a tenant can register an agent and set its `capabilities` via the raw API today, but there's no dashboard surface for it, and no guidance on what a "correct" capability list looks like for a given integration. Functionally complete, operationally still self-serve-by-API only.
- **`requested_scopes` on `/governance/decision` is still always empty**, regardless of whether a real `agent_id` is supplied — so a registered agent's `scopes` field (as opposed to its `capabilities`) stays decorative until the endpoint itself accepts a caller-declared scopes list to check against it. `action_within_capabilities` and `user_rbac` are both real now for a supplied `agent_id`; `scopes_exist` (PreFilter `CHECK 4`) is not yet, for the same reason it never was.

Already mitigated, despite sometimes being assumed otherwise:
- A real automated test suite (37 tests across 8 files) and CI (GitHub Actions, running against a live Postgres service container on every push/PR to `main`) have existed since 2026-08-23 — not "verified live against production only."
- A versioned changelog for the PAN/ECM/PFM/SDA scoring calibration (`cgc_calibration_changelog`, `/calibration/*` — see API surface above) has existed since 2026-09-11. Every change to a scoring rule is admin-only and requires a `reason`; nothing updates calibration without also writing its own history entry.
- `GET /governance/scoring-methodology` (since 2026-09-11) explains, in one response, the exact formula and every weight used to turn module scores into an APPROVE/REJECT/REQUIRE_HUMAN decision — no need to read `cgc_loop.py` to audit how a decision was reached.
- **Google OIDC login** (since 2026-09-12): `AuthSystem.login_federated()` + `/auth/google/*` — CSRF-protected via a signed state cookie, ID token verified against Google's real JWKS via the official `google-auth` library (never hand-rolled), auto-provisions an account with a permanently-unusable random password on first login. Verified live up to the Google-consent boundary (status/login/CSRF rejection all correct); the actual browser consent screen needs the user's own Google Cloud OAuth client credentials to exercise end-to-end.
- **Enterprise SAML SSO** (since 2026-09-12): `/auth/saml/*` + `cgc_saml_connections` — one Identity Provider connection per customer email domain, all cryptographic assertion verification via `python3-saml`/`xmlsec` (never hand-rolled), reuses the same `login_federated()` session-issuing path Google uses. Verified live against production: admin can create a connection, `/auth/saml/lookup` correctly reports availability, `/auth/saml/{domain}/login` redirects to that domain's real IdP with a well-formed `AuthnRequest`, `/auth/saml/metadata` returns valid SP metadata XML. The actual signed-assertion round-trip needs a real Okta/Azure AD trial tenant to exercise end-to-end — same category of user-side dependency Google's consent screen has.
- The EU AI Act checks in `ComplianceEngine.validate_eu_ai_act` are real logic as of 2026-09-11, not hardcoded placeholders — see the method's own docstring for exactly which 4 of the 7 requirements are runtime-verifiable (and are), and why the other 3 honestly report `MANUAL_REVIEW_REQUIRED` instead of a fabricated PASS.
- `GET /compliance/glba-safeguards` (since 2026-09-11) is a real FTC Safeguards Rule self-assessment scoped to what actually applies (GLBA, via LedgiProof/LedgiProof Tax Pro as tax preparers) — HIPAA and FINRA are explicitly reported as not applicable to any current consumer, with the regulatory reasoning, rather than building decorative checklists for frameworks nothing here is subject to.
- **Self-serve tenant onboarding** (since 2026-09-11): `POST /tenants/self-signup` lets any authenticated non-admin user (via the existing `/auth/signup`) claim their own brand-new `app_source` and get an API key + FREE billing stub, with no admin action needed. Reserved first-party names can't be self-claimed, an already-claimed `app_source` returns 409, and format/rate limits apply — verified live end-to-end (claim, collision, reserved-name, bad-format, unauthenticated all return the correct status).
- **A real customer-facing settings page** (`GET /dashboard/account`, since 2026-09-11): claim an app, view your own keys, regenerate/revoke them, upgrade or manage your own billing — all ownership-checked (`created_by` match), not `require_admin`. Before this, self-signup only existed as an API call with no UI, and there was no way for a non-admin to ever see or rotate their own key again after the one-time reveal. Verified live: two disposable non-admin accounts, cross-account ownership correctly rejected (403), own-account regenerate/revoke both correct.
- **Outbound webhooks** (since 2026-09-12): one URL per `app_source`, HMAC-SHA256-signed (`X-CGC-Signature`), delivered from inside `/governance/decision` itself with a 5s timeout — verified live with a real local HTTP receiver (signature matched byte-for-byte). A failed delivery now queues for retry (see below) instead of being silently lost.
- **A real usage panel** (since 2026-09-12): `/tenants/my-apps` now returns `decisions_used`/`decisions_quota` per app, backed by a NEW counter namespaced `app_source:<name>` inside `cgc_guard.tenant_usage` — deliberately separate from the org_id-keyed quota-enforcement counters `check_quota`/`reserve_quota` already used, so this is purely additive and can't affect real rate-limiting.
- **Key-rotation advance notice, not forced rotation** (since 2026-09-12): `/tenants/my-apps` flags any active key ≥90 days old (`rotation_recommended`), shown in the dashboard; `POST /admin/keys/rotation-check` (cron-callable) Slack-alerts an operator about the same. Deliberately does NOT auto-rotate anything — there's no per-customer notification channel yet, so silently swapping a live key on a timer could break production traffic with no way to warn the holder first.
- **A real, hand-written integration guide** (`GET /docs/getting-started`, since 2026-09-12) — signup → self-signup → first decision → webhook signature verification → rate limits, with real curl examples against the actual live endpoints above. The auto-generated Swagger at `/docs` documents every field; this explains the flow.
- **Python and TypeScript/JavaScript SDKs** (`sdk/python/`, `sdk/js/`, both `cgc-core-sdk`, since 2026-09-14) — wrap the self-service surface (auth, decisions, monitoring, launch readiness, webhooks, weighting overrides). Python: 7 unit tests, mocked HTTP. JS: 8 unit tests (`node:test`) against the compiled `dist/` output a consumer actually gets.
- **A written API versioning policy** (`docs/API_VERSIONING_POLICY.md`, since 2026-09-14) — path-based `/v2` prefixes for future breaking changes, 90-day minimum deprecation window, `Deprecation` headers, classified breaking-vs-non-breaking changes. Corrects a real misconception along the way: `root_path="/api/v1"` was never a real path prefix, only cosmetic for OpenAPI doc URLs.
- **Webhook delivery retry queue** (`cgc_webhook_retry_queue`, `POST /admin/webhooks/process-retries`, since 2026-09-14) — 5-tier backoff (5m/15m/1h/4h/24h), 5 attempts max, run every 10 minutes by `.github/workflows/webhook_retries.yml`.
- **Per-tenant decision-weighting overrides** (`cgc_tenant_weighting_overrides`, `/tenants/my-apps/{app_source}/weighting/*`, since 2026-09-14) — the area+sensitivity matrix, previously only changeable by editing `cgc_loop.py` and redeploying, is now API-configurable per tenant, ownership-checked, falling back to the global default when unset.
- **Dependency CVE sweep** (2026-09-14): pip-audit found 165 known vulnerabilities across 21 packages; all patched (aiohttp needed the 3.14.x line specifically, not just a patch release) and verified with a real install (fresh venv, zero conflicts) plus the full test suite green. `PyPDF2` removed outright rather than "upgraded" to a version pip-audit suggested that turns out not to exist (verified against PyPI directly) — it wasn't imported anywhere in this codebase anyway.
- **`JWT_SECRET` now fails closed in production** (`AuthSystem.__init__`, since 2026-09-14) — used to silently fall back to a fresh per-process ephemeral secret in every environment including production, on nothing louder than an unmonitored `print()`. Now raises if `VERCEL_ENV=="production"` and `JWT_SECRET` is unset; dev/preview keep the ephemeral fallback.
- **Self-signup tenants can now actually use monitoring and launch readiness** (`/monitor/*`, `/launch-readiness/*`, since 2026-09-14) — every route in both files checked ONLY the static `ALLOWED_APP_SOURCES` allowlist, rejecting every self-signup `app_source` outright (worse in `/monitor/*`: `GET /errors`/`/errors/stats`/resolve/delete had no ownership scoping at all — any authenticated caller could read or mutate another tenant's error reports by passing a different `app_source`). - **AI-agent action-governance stack, 4 parts, all closed 2026-09-15.** PreFilter validated agent existence/RBAC/scopes/status since this module's creation, but never validated that the *action itself* was one the caller was actually granted — an agent whose declared capabilities never included e.g. `transfer_funds` could still submit `action="transfer_funds"` and pass every other check. Closed as four layered, independently-verified controls, each real containment (denies the request), not just detection (logs and reports):
  1. **`action_within_capabilities` check** (PreFilter `CHECK 4B`, `app/modules/prefilter/PreFilter.py`) — the requested action must be in the agent's declared `capabilities` list. Ships with a safety valve (an agent with an empty capabilities list — today's only real production shape, see the gap above — is treated as vacuously passing, same convention the pre-existing scopes check already used for an empty `requested_scopes`), found and fixed *before* shipping by tracing the real call site: the naive, unconditional version would have denied 100% of production traffic.
  2. **Circuit breaker** (`app/modules/guard/circuit_breaker.py`, `cgc_guard.circuit_breaker_state`) — standard closed/open/half-open state machine. N PreFilter short-circuit denials from the same `(org_id, user_email)` within a trailing window trips it OPEN, denying every further request from that pair immediately (before PreFilter runs a single check) until a cooldown elapses, then lets one HALF_OPEN trial through. Dashboard + manual reset at `GET`/`POST /guard/activity/circuit-breakers[/reset]` (operator-only).
  3. **Tenant action policies** (`app/modules/guard/tenant_policy.py`, `cgc_tenant_action_policies`) — self-service, per-tenant BLOCK / REQUIRE_HUMAN_REVIEW rules for a given action, optionally conditioned on area and/or data domains. A distinct axis from both of the above: not agent-level or code-defined, a business decision the tenant itself makes about their own data, independent of how any agent happens to be configured. `GET`/`PUT`/`DELETE /tenants/my-apps/{app_source}/action-policies[/{action}]`, ownership-checked like weighting overrides.
  4. **Kill switch** (`app/modules/guard/kill_switch.py`, `cgc_guard.kill_switch_state`) — an unconditional emergency stop, checked *first*, ahead of the circuit breaker and tenant policies, since the entire point is that it works without a request needing to look any particular way, a threshold to trip, or a code deploy. `GLOBAL` scope (platform-wide, operator-only, `/guard/activity/kill-switches`) or a real `app_source` (self-service, same ownership model, `/tenants/my-apps/{app_source}/kill-switch/*`). Deliberately the one guard module in this codebase that fails **closed**, not open, on a DB error (`CGC_KILL_SWITCH_FAIL_CLOSED`) — every other check here degrades to "allow" if its own infrastructure breaks, but a kill switch has to still work at exactly the moment something else already has.

  All four verified against real, disposable Postgres containers (never assumed from code-reading): direct state-machine scenarios for each layer, full end-to-end HTTP runs through `/governance/decision` covering the real check order (kill switch → circuit breaker → tenant policy → PreFilter) and confirming legitimate traffic is never falsely tripped, the self-service/admin endpoints against real ownership enforcement, and the full pytest suite with no regressions at every step.
- **Real agent registry** (`cgc_agents`, same day, closing the root cause behind the whole stack above) — until this, `run_cgc_prefilter` always synthesized a permissive per-request `Agent` (`capabilities=[]`, `roles==caller's own role`) because there was nowhere real to look one up from; that's *why* `action_within_capabilities` had nothing to actually enforce for any real caller before today. `POST /governance/decision` now accepts an optional `agent_id`: omit it and every current integration (LedgiProof, ControlMiles, Xolphi) keeps today's exact behavior unchanged; supply one that resolves to a real, tenant-owned agent (self-service CRUD at `GET`/`POST /tenants/my-apps/{app_source}/agents` + `GET`/`PUT`/`DELETE .../agents/{agent_id}`) and PreFilter evaluates against that agent's real `roles`/`scopes`/`capabilities` instead — `user_rbac` (`CHECK 3`) becomes a genuine check rather than vacuously true, and `action_within_capabilities` (`CHECK 4B`) enforces something real. An `agent_id` that doesn't resolve, or belongs to a different `app_source`, is a hard DENY, never a silent fallback to the permissive default — verified live: a real agent denied for an action outside its declared capabilities, a nonexistent `agent_id` denied, a cross-tenant `agent_id` denied, a real RBAC mismatch (agent requires `admin`, caller has `user`) denied, and a request with no `agent_id` at all still approved exactly as before. `requested_scopes` still isn't wired to this (see Known Gaps above) — `scopes_exist` stays inert even for a real agent.
